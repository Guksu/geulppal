# 조사 근거와 설계 판단

조사일: 2026-10-27. 공개 자료와 사용자가 요청한 이전 README 편집 사례를 검토했다. 아래 내용은 스킬 설계의 근거이며, 새 스킬의 성능을 측정한 결과가 아니다. 외부 스킬의 지시문이나 예문을 복제하지 않고 이 프로젝트의 규칙과 예시를 작성했다.

## 실제 README 수정에서 배운 점

[suta PR #44](https://github.com/Guksu/suta/pull/44)의 한영 README diff를 직접 확인했다. 이 PR은 참고 사례다. 현재 스킬로 수행한 결과가 아니다.

| 관찰한 수정 | 이번 스킬에 반영한 기준 |
|---|---|
| 설치하면 UI를 만들 때마다 읽는다는 설명을 실제 제공 기준·패턴 설명으로 수정 | 자동 적용과 효과를 실제 동작보다 넓게 약속하지 않기 |
| ‘검색 입구’, ‘머리의 검색 칸’을 검색창·헤더 검색창으로 수정 | 전문용어를 무리하게 풀어 쓰지 않기 |
| 만드는 시간·빌드 시간을 생성 시간으로 정리 | 수치뿐 아니라 측정 대상과 지표 이름도 검토하기 |
| 비교 결과에 자동 검사 범위, 모델 평가, 표본 한계를 명시 | 개별 측정 결과를 전체 품질 보장으로 확대하지 않기 |
| 반복되는 기능 설명을 합치고 상세 문서로 연결 | 정보 탐색에 필요한 구조를 유지하면서 중복 줄이기 |

이전 대화에서는 소개글이 복잡하다는 피드백, 만든 이유를 도입에 넣어 달라는 요청, 계속 업데이트한다는 계획을 남겨 달라는 요청도 확인했다. 이를 ‘짧게 쓰더라도 저자가 알려준 동기와 약속을 유지한다’는 기준으로 반영했다. 대화 식별자와 전체 대화 내용은 포함하지 않았다.

과거 수정안을 정답으로 고정하지 않는다. 특히 실제 diff에는 일부 세부 내용이 생략된 부분도 있다. 이번 스킬은 단순 윤문에서 의미를 보존하고, 요약 요청에서는 요청 범위 안에서 내용을 선택하도록 구분한다.

## 공개 스킬 비교

### Humanizer

자료: [blader/humanizer의 SKILL.md](https://github.com/blader/humanizer/blob/main/SKILL.md).

문장 단위의 상투어뿐 아니라 문단 구조, 과장, 대화 잔재를 살피고 수정 후 사실 손실을 다시 점검한다. 참고 문체가 있다면 이를 우선한다. 구조를 먼저 보는 접근과 보존 검사를 참고했다.

이 스킬의 붙여 넣은 글에 대한 기본 출력은 중간 초안과 남은 패턴, 최종문을 함께 제시한다. 이번 프로젝트는 사용자가 바로 쓸 완성문을 기본으로 반환한다. 특정 패턴을 발견했다는 이유만으로 수정하지 않고 문맥에서 정보가 있는지 판단한다.

### Korean Humanizer

자료: [dotoricode/korean-humanizer의 SKILL.md](https://github.com/dotoricode/korean-humanizer/blob/main/SKILL.md).

한국어 번역투와 약한 서술어를 다루고 행위·성과·확신의 범위를 보존하는 지침이 있다. 기술 문서 등은 적용 범위에서 제외하며 기본 결과 형식을 지정한다.

이번 프로젝트는 README·기술 설명·PR을 주요 용도로 삼는다. 문서의 독자와 형식에 따라 편집하되 별도의 고정 결과 틀은 요구하지 않는다.

### Humanizer KO

자료: [choconyam/humanizer-ko의 SKILL.md](https://github.com/choconyam/humanizer-ko/blob/main/SKILL.md).

한국어를 중심에 두고 영어 지침을 별도 참조로 다룬다. 시제·확정 여부·부정·범위·완료 상태와 기술 표기를 보존하는 기준이 구체적이다.

이러한 의미 보존을 이번 설계에서도 우선한다. 새 글 작성에는 입력된 사실을 사용하고, 편집에는 원문과 수정본의 주장 범위를 대조하는 흐름을 둔다.

### Korean Skills의 Humanizer

자료: [daleseo/korean-skills의 humanizer](https://github.com/daleseo/korean-skills/blob/main/skills/humanizer/SKILL.md).

쉼표·띄어쓰기·품사·번역투 등 한국어 특징을 분리하고 연구와 연결해 설명한다. 한국어를 영어 상투어 목록의 번역만으로 다루지 않는 점을 참고했다.

이번 프로젝트에서는 패턴 수에 따른 자연도 등급이나 검출 확률을 제공하지 않는다. 연구에서 측정한 분류 성능과 편집된 글의 품질은 다른 대상이다. 맞춤법을 일부러 틀리게 하거나 쉼표를 정해진 비율로 줄이는 방식도 사용하지 않는다.

## 글쓰기 원칙과 연구

### Google 개발자 문서 지침

자료: [Voice and tone](https://developers.google.com/style/tone), [Clear sentences](https://developers.google.com/tech-writing/one/clear-sentences).

독자에게 필요한 정보를 명료하게 전달하고, 상투적 표현·부풀린 표현·과도하게 끊기는 문장을 피하는 기준을 참고했다. 구체적인 동사를 쓰되 전문 독자에게 필요한 용어는 남긴다. 수식 대신 측정치를 쓰는 방법은 실제 수치가 주어졌을 때만 적용한다.

기술 문서용 문체를 에세이·개인 소개글 전체에 강제하지 않는다. 이는 문서 종류별 지침을 분리한 이유다.

### Wikipedia의 AI 문체 관찰 목록

자료: [Wikipedia:Signs of AI writing](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing).

과장된 중요성, 홍보성 문구, 모호한 귀속, 구조와 서식의 반복, 대화용 문구가 남는 현상을 참고했다. 위키백과 편집 맥락의 관찰 목록을 모든 글에 적용되는 판별기로 사용하지 않는다. 표·굵은 글씨·부정 대조는 실제 용도가 있으면 남긴다.

### KatFishNet

자료: [Park 외, KatFishNet, arXiv v5](https://arxiv.org/abs/2503.00032v5).

초록과 서지 정보를 확인했다. 연구는 한국어의 띄어쓰기, 품사 다양성, 쉼표 사용을 분석하고, 세 장르와 네 LLM으로 구성한 데이터셋에서 생성 텍스트 검출을 다룬다. 한국어를 별도로 다룰 근거는 되지만, 특정 문장이 나쁜 글이라는 판정이나 이 스킬의 개선 효과를 증명하지 않는다. 본문의 상세 실험 수치를 재현하거나 검증하지 않았으므로 이 프로젝트의 품질 수치로 사용하지 않는다.

## 패키지 형식

자료: [Claude Code skills](https://code.claude.com/docs/en/skills), [Claude custom skills 작성 안내](https://support.claude.com/en/articles/12512198-how-to-create-custom-skills).

`SKILL.md`의 name·description과 상대 경로 참조 파일로 구성한다. Claude Code에서는 개인 또는 프로젝트의 `.claude/skills/`에 설치한다. Claude 업로드용 ZIP에는 이름이 같은 스킬 폴더를 최상위에 넣는다. 새 스킬은 일반적인 자동 선택을 허용하며, 등록 후 명시적으로 호출할 수도 있다. 실제 자동 선택 여부는 별도로 확인해야 한다.

## 이번 버전에서 검증할 가설

- 동작과 근거를 먼저 쓰는 지침이 단순한 금지어 치환보다 내용 이해에 도움이 되는가?
- 한영 문서의 사실·조건·말투를 유지하면서 반복과 과장을 줄이는가?
- 충분히 좋은 문장, 기술적인 부정문, 실제 세 항목 목록을 과도하게 수정하지 않는가?
- 새 글 작성과 기존 글 편집 모두에서 근거 없는 기능·성과·개인 경험을 추가하지 않는가?

평가 입력과 판정 기준은 [평가 안내](../evals/README.md)에 둔다. 현재는 가설이며 모델 간 우열이나 효과 크기를 주장하지 않는다.

## 문장 비교

### Claude Code 답변 다듬기 (글빨 0.5.2)

Claude Code(`claude-sonnet-5-5`)에 개발 질문과 일상 질문 12개를 한국어로 했습니다. 공개 저장소 코드에 대한 질문(새 팀원 안내, 팀장 보고, PR 설명), 저장소 없이 묻는 개발 질문(git, DB 인덱스, async/await, Docker), 개발자가 아닌 사람의 질문(전세와 월세, 운동)입니다. 글빨 없이 받은 답변을 다시 "내용은 그대로 두고 한국어로 자연스럽게 다듬어 줘"라고 맡겼고, 한쪽은 글빨 없이, 다른 쪽은 글빨 0.5.2로 다듬었습니다. 사례는 결과를 보기 전에 만들었습니다.

아래는 판정 모델이 어색하다고 표시한 문장과, 0.5.2로 다듬은 1회차 결과에서 같은 자리입니다.

| 사례 | 글빨 없이 쓴 답변 | 글빨 0.5.2로 다듬은 결과 |
|---|---|---|
| 형태소 분석기 보고 | 마지막 단어 뒤에 넣을 insert 패치는 조용히 버려집니다. | 마지막 단어 뒤에 넣을 insert 패치는 오류 없이 버려집니다. |
| 저장소 래퍼 보고 | 값이 외부에서 바뀌거나 오염되면 타입이 거짓이 됩니다. | 값이 외부에서 바뀌거나 오염되면 타입이 실제 값과 맞지 않게 됩니다. |
| 모델 패키지 안내 | 구조를 바꾸면 조용히 틀린 결과가 나올 수 있습니다. | 구조를 바꾸면 오류 없이 틀린 결과가 나올 수 있습니다. |
| 모델 패키지 안내 | `return_dict`를 건드리면 하위 사용처가 깨집니다. | `return_dict`를 건드리면 이 출력을 쓰는 코드가 깨집니다. |
| 에러 수집 PR 설명 | 아래 초안은 소스에서 확인한 테스트 공백을 기준으로 썼습니다. | 아래 초안은 소스에서 확인한, 테스트가 없는 부분을 기준으로 썼습니다. |
| HTTP 클라이언트 안내 | ESM 빌드에서는 esbuild의 `require` 심이 던질 수도 있습니다. | ESM 빌드에서는 esbuild가 넣는 `require` 대체 코드(shim)가 오류를 낼 수도 있습니다. |
| 전세와 월세 | 목돈이 부족하거나 이동 가능성이 크다면 월세가 낫습니다. | 목돈이 부족하거나 이사할 가능성이 크다면 월세가 낫습니다. |
| 운동 시작 | 운동 중 가슴 통증, 심한 어지럼증, 극심한 숨참이 있으면 바로 중단하세요. | 운동 중에 가슴 통증, 심한 어지럼증, 매우 심한 숨 가쁨이 나타나면 바로 멈추세요. |

고쳐지지 않고 남은 곳도 있습니다.

| 사례 | 다듬은 뒤에도 남은 문장 | 판정 모델이 짚은 곳 |
|---|---|---|
| 에러 수집 PR 설명 | 이 PR은 동작을 바꾸지 않고 테스트만 추가해 이 부분을 보호합니다. | `보호합니다`(protect): `회귀를 막습니다`가 더 자연스럽다 |
| HTTP 클라이언트 안내 | `dts.resolve: true`도 같은 전제입니다. | 무엇이 같은 전제인지 풀어 써야 한다 |
| 한글 라이브러리 PR 설명 | 현재 동작을 고정하는 테스트를 넣지 않았습니다. | `고정하는`(pin): `현재 동작을 기대값으로 삼는` |

### 글빨 없이 다듬으면

글빨 없이 같은 요청을 하면 어색한 표현이 남거나 뜻이 바뀌는 경우가 있었습니다. 아래는 앞선 새 확인용 사례에서 나온 결과입니다.

| 사례 | 원래 답변 | 글빨 없이 다듬은 결과 | 무엇이 바뀌었나 |
|---|---|---|---|
| 발음 변환 패키지 성능 | `G2p()` 생성이 느리고 메모리도 씁니다. 서버나 CLI에서 `G2p()`를 요청마다 새로 만들면 가장 비싼 실수가 됩니다. | `G2p()` 생성이 느리고 메모리도 많이 씁니다. 서버나 CLI에서 요청마다 `G2p()`를 새로 만들면 가장 비싼 실수가 됩니다. | 원래 없던 `많이`가 들어갔고, `가장 비싼 실수`(the most expensive mistake)는 그대로 남았다 |
| 말뭉치 패키지 버그 | 이 연결은 닫히지 않고, `urlretrieve`가 두 번째 요청을 따로 보냅니다. | 이때 연결은 닫히지 않고, `urlretrieve`가 두 번째 요청을 따로 보냅니다. | `이때`로 바뀌어, 늘 생기는 문제가 헤더가 없을 때만 생기는 문제처럼 읽힌다 |

## 평가 요약

| 결과를 보기 전에 만든 사례 | 글빨 없음 | 0.5.1 | 0.5.2 |
|---|---|---|---|
| 새 확인용 8개 × 2회, 다듬기: 표시된 표현이 그대로 남은 수 | 19/34 | 4/34 | |
| 같은 다듬기: 뜻을 지킨 결과 | 12/16 | 16/16 | |
| 2차 새 확인용 12개 × 2회, 다듬기: 표시된 표현이 그대로 남은 수 | 18/48 | 8/48 | 8/48 |
| 같은 다듬기: 뜻을 지킨 결과 | 22/24 | 22/24 | 23/24 |
| 2차 새 확인용, 처음부터 쓰기(1회): 1,000자당 표시된 곳 | 1.15 | 0.86 | 0.86 |

- 다 쓴 답을 다듬게 할 때는 두 사례 묶음 모두에서 효과가 분명했습니다.
- 처음부터 쓰게 할 때는 엇갈렸습니다. 2차 새 확인용에서는 표시가 줄었지만, 첫 새 확인용 8개에서는 줄지 않았습니다(글빨 없음 34곳, 0.5.1 36곳).
- 0.5.0은 기술 용어를 우리말로 옮기는 문제(key → `열쇠`, feature → `특징`)를 새로 만들었고, 0.5.2는 기술 개념의 이름은 옮기지 않는다는 원칙을 따로 세웠습니다.
- 자동 선택: 한국어 글을 다듬어 달라는 요청 18/18, 영어 문서 요청 0/2, 고르지 말아야 할 요청 0/16.
- 새로 쓸 때의 내용 규칙을 참고 문서로 옮긴 뒤 README 초안 4개를 다시 확인했을 때, 코드에 근거가 있는 내용만 쓴 결과는 0.5.2가 8/8, 0.4.1이 7/8이었습니다.
- 실행당 비용은 다듬기가 글빨 없이 할 때의 약 2~2.3배, 쓰기가 약 1.2~1.8배입니다.

## 판정 방법

판정 모델(`claude-opus-5-5`)이 글을 읽고 독자가 멈칫할 곳을 종류(낱말대로 옮긴 말, 설명 없는 이름, 명사 나열, 기호로 대신한 설명, 번역투, 그 밖의 어색함)와 정도로 표시했습니다. 업계에서 그대로 쓰는 외래어, 코드 이름, 취향 차이는 표시하지 않습니다. 다듬기는 원래 글과 뜻이 같은지도 따로 판정했습니다. 표시한 곳의 수는 글의 품질 점수나 AI 작성 확률이 아닙니다. [판정 지침](../evals/judge/korean-natural.md)

## 한계

- 판정 모델 하나가 표시했습니다. 판정 모델이 표시한 문장과 표시하지 않은 문장 10개를 저장소 소유자가 직접 골랐을 때 7개가 일치했습니다. 판정 모델은 `회귀`처럼 개발자가 실제로 쓰는 번역어를 과하게 잡는 경향이 있었습니다.
- 사례가 적습니다(8개, 12개). 질문은 평가 작성자(모델)가 썼습니다.
- 실행마다 결과가 달라집니다. 같은 스킬도 CLI 버전에 따라 결과가 달랐습니다(0.4.3의 블로그 사례 4개 × 2회에서 2.1.312로 7/8, 2.1.314로 4/8).
- Claude Code와 `claude-sonnet-5-5`에서만 평가했습니다.
- 0.5에서 보고서·블로그 초안은 다시 재지 않았습니다.

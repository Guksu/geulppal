# 글빨 평가 보고서 (2026-10-27)

Claude Code에 글빨을 쓰지 않은 조건(A)과 쓴 조건(B)을 같은 요청으로 비교했다. 정확성(의미 보존), 글의 품질, 자동 선택, 시간·비용을 따로 보고한다. 판정은 모두 모델(`claude-opus-5-5`)이 했고 사람의 평가는 하지 않았다. 표본이 작으므로 아래 수치는 이 사례들에서 관찰한 결과다. 일반적인 우월성을 뜻하지 않는다.

방법과 재실행 명령은 [평가 안내](../README.md)에 있다. 사례마다 원문과 조건별 결과를 나란히 보려면 [사례별 결과](README.md)를 연다.

  - 품질(개발 사례): 두 결과가 모두 의미 보존을 통과한 쌍에서 판정자는 B0를 12쌍, A를 3쌍 골랐다.

- **나빠졌거나 나아지지 않은 것**
  - 처음 보는 사례에서는 B0와 B2의 차이가 확인되지 않았다(의미 보존 19 대 18, 품질 3쌍 대 3쌍).
  - v0.2.0에서는 개발 사례 `draft-from-facts`에서 원문에 없는 기능 표현("메모를 한곳에 모으고")이 4회 중 2회 나왔다. 초기 버전과 A에서는 나오지 않았다.

- **확인하지 못한 것**
  - 사람 독자의 평가와 다른 작성 모델을 쓴 경우
  - 파일을 직접 고치는 작업의 품질
  - 2,000자보다 긴 문서
  - 영어 요청의 자동 선택 개선(약점은 확인했고 고치지 않았다)

## 1. 조건

- 작성: Claude Code CLI 2.1.311, `claude -p`, `claude-sonnet-5-5`, `--effort high`, 도구 Read·Glob·Grep·Skill. 실행 기록의 모델 식별자는 모든 실행에서 `claude-sonnet-5-5`였다.
- 격리: 실행마다 임시 HOME·CLAUDE_CONFIG_DIR·작업 폴더를 새로 만들고, 새 세션 ID를 쓰고, MCP를 쓰지 않았다(`--setting-sources project --strict-mcp-config`). 그 결과는 다음과 같다.
  - 모든 실행에서 새 세션 ID를 확인했다.
  - MCP 서버는 0개였고, 계정 동기화 스킬은 들어오지 않았다.
  - 내장 플러그인 3개와 CLI 기본 스킬은 조건 사이에 같았다.
  - 실행 폴더 경로를 지운 시스템 프롬프트는 모든 조건에서 해시가 같았다.
- 스킬 적용: B 조건 실행 152회 전부(시험 4회, 개발 B0 38·B1 24·B2 38회, 처음 보는 사례 B0 24·B2 24회)에서 대화 기록으로 `/geulppal` 펼침과 설치한 `SKILL.md` 본문 주입을 확인했다. 참조 문서는 약 절반의 실행에서 읽었다. 스킬을 읽지 않은 실행은 없었다.
- 실행 실패: 품질 평가 실행 218회에서 실패·시간 초과·권한 거절·출력 누락은 0회였다. 실패 기록이 남는지 확인하려고 일부러 시간 초과를 낸 1회와 그 재시도 1회는 [`2026-10-27-pipeline-check`](2026-10-27-pipeline-check/report.md)에 따로 있다.
- 판정: `claude-opus-5-5`, `--effort high`, 도구 없는 새 세션. 판정 716회에 실패는 0회였다.
  - 의미 보존: 결과마다 한 번 판정했다. 처음 보는 사례는 두 번 판정했다.
  - 품질: 두 결과가 모두 의미 보존을 통과한 쌍만, 순서를 바꿔 두 번 판정했다.
  - 작성 모델과 판정 모델은 다르지만 같은 회사의 모델이다.

## 2. 개발 사례: A와 B0

개발 사례 19개는 초기 사례 12개와 보충 사례 7개다. 이 가운데 9개는 스킬 예문과 같은 상황을 다루고, 모두 스킬을 읽은 사람이 썼다. 그래서 독립적인 성능 근거로 쓰지 않는다. 결과 전체는 [`2026-10-27-dev/report.md`](2026-10-27-dev/report.md)에 있다.

**정확성**: A는 38회 중 10회, B0는 1회 실패했다. A가 한 번 이상 실패한 사례는 6개다.

| 사례 | A의 실패 내용(판정 근거 요약) |
|---|---|
| `pr-technical-literals` | "8개가 통과"를 "8개가 모두 통과"로 써서 실패·건너뜀이 없다는 주장을 만듦(2/2) |
| `proposal-cost-exceptions` | "검토"를 "추진하고자 함"으로 강화, "응답 속도를 높이고", "측정하여 보고하겠습니다" 같은 목적·약속 추가(2/2) |
| `pr-body-mixed-terms` | 원문에 없는 "리뷰 시 봐주세요" 섹션과 기술적 우려를 본문에 추가(2/2) |
| `personal-blog-voice` | 두 문장을 합치며 "그것이"의 지시 대상이 바뀌어 작성자의 결론이 달라짐(2/2) |
| `missing-evidence` | 측정 자료 없이 "성능도 크게 개선되었습니다"로 단정(1/2) |

B0의 실패 1회는 `missing-evidence`다. 본문에 원문에 없는 약속("측정이 끝나면 결과를 따로 알리겠습니다")을 넣었다.

**품질**: 38쌍 중 27쌍을 비교했다. 11쌍은 한쪽 이상이 의미 보존에 실패해 뺐다.

사례 단위로 보면 승패가 난 회차가 모두 B0 쪽인 사례가 6개, 모두 A 쪽인 사례가 0개, 엇갈린 사례가 3개다. 나머지 10개는 승패가 나지 않았다.

### 대표 실패

**1. 작성 과정의 사정과 새 약속이 공개용 본문에 들어감 (B0 `missing-evidence` 2회차)**

- 요청: "출시 소개글을 써줘. 성능이 크게 좋아졌다는 설명은 들었지만 측정 수치는 아직 없어. 짧게 쓸 수 있는 범위까지만 써줘."
- 결과 본문: "이번 버전은 성능도 크게 좋아졌다는 설명을 받았습니다. 다만 측정한 수치는 아직 없어서 이번 글에는 싣지 않았습니다. 측정이 끝나면 결과를 따로 알리겠습니다."
- 문제: 사용자에게 할 말이 출시 소개글 본문에 들어갔다. 원문에 없는 약속도 생겼다. 1회차에도 "좋아졌다고 들었습니다"가 본문에 있었다.
- 원인 가설: v0.1.0의 "주장 귀속을 남기거나 문서 밖에서 확인할 부분을 짧게 알린다"를 본문 안의 귀속으로 적용했다. 본문과 메모를 나누는 지침도 없었다.
- 수정: 본문은 원래 작성자의 목소리로 쓰고, 편집 과정과 새 약속은 본문에 넣지 않는다. 확인할 점은 본문 밖에 적는다.
- 재검증: v0.2 계열 4회(B1 2회, B2 2회)에서 같은 문제가 다시 나오지 않았다. 다만 B2는 본문에 "성능도 개선되었습니다"를 남겼고, 판정자는 이를 원문 요청의 주장으로 보고 통과시켰다.

**2. 근거보다 넓은 결론을 좁히지 않고 지움 (B0 `benchmark-scope` 2회차)**

- 원문 첫 문장: "A가 압도적으로 뛰어났습니다." 이어지는 근거는 axe 위반 6건 대 24건, 생성 시간 65초 대 40초다.
- 결과: 첫 문장을 지우고 수치만 남겼다. 결론 문장은 메모에서 제안했다.
- 판정: A 우세. A는 "접근성 면에서는 A가 더 우수했습니다 … 반면 A가 더 느렸습니다"로 결론을 남겼다. 판정자는 B0 결과를 두고 "결론을 아예 빼서 독자가 직접 추론해야 한다"고 했다.
- 원인 가설: v0.1.0 `editing-examples.md`의 측정 예시가 "도구 A의 압도적인 성능을 확인했습니다"를 통째로 지운 수정을 보여 준다. 같은 스킬의 "조용히 삭제하지 말라"는 기준과 충돌한다.
- 수정: 결론이 근거보다 넓으면 지우기보다 근거가 받치는 범위로 좁힌다. 예시는 다른 분야(이미지 캐시와 로딩 시간)의 것으로 바꿔 평가 사례의 답이 스킬에 들어가지 않게 했다.
- 재검증: v0.2 계열 4회 중 3회가 결론을 좁혀 남겼다. 그러나 B2 1회차는 좁힌 결론 뒤에 같은 수치를 다시 써서, 판정자가 "반복이 남았다"며 B0를 골랐다.

**3. 요청하지 않은 편집 설명 (B0 `quotation-and-opinion` 2회차)**

- 결과: 본문 뒤에 "마지막 문장은 앞의 '불편합니다'를 되풀이해서 뺐습니다. 인용문과 의견, 이유는 그대로입니다."를 붙였다.
- 판정: A 우세. "사용자가 이 글을 그대로 쓰려면 이 부분을 직접 지워야 한다."
- 수정: 무엇을 바꿨는지는 사용자가 물었을 때만 설명한다. 사용자가 채우거나 확인해야 할 것이 있을 때만 짧게 덧붙인다.
- 재검증: B2 2회 모두 본문만 돌려줬다.

**4. 수정이 만든 회귀 (B1 `readme-long-repetition` 2회차)**

- 요청: "README를 다듬어줘. … 마크다운으로 결과만 줘."
- 결과: README 뒤에 "원문의 '팀의 생산성 향상에 중요한 역할을 합니다'는 근거가 없어 뺐습니다. …"를 붙였다. 요청 범위를 벗어나 의미 보존 실패가 됐다. B0는 2회 모두 결과만 줬다.
- 원인: 1라운드에서 메모를 붙여도 되는 경우로 "되돌리고 싶을 수 있는 삭제"를 허용했다. 일상적인 삭제까지 설명하게 만든 과도한 지침이었다.
- 수정(2라운드): 메모는 원문에 없어 비워 둔 사실과 하나로 고를 수 없는 해석에만 붙이고, 결과만 달라는 요청에는 붙이지 않는다.
- 재검증: B2 2회 모두 README만 돌려줬다.

**5. 해결되지 않은 악화 후보 (B1·B2 `draft-from-facts` 1회차)**

- 입력: "기능: 태그 검색, CSV 내보내기 … 저장 방식은 제공하지 않음"
- 결과: "그래서 메모를 한곳에 모으고 태그로 찾을 수 있게 만들었습니다. 모아 둔 메모는 CSV로 내보낼 수 있습니다."
- 문제: 원문에 없는 수집 기능을 썼다. v0.2 계열 4회 중 2회 나왔고 B0·A에서는 0회였다.
- 원인 가설: 확인하지 못했다. 표본이 작아 우연일 수도 있다. 같은 사례의 2회차에서는 도입 문장이 기능 설명을 되풀이하는 문제가 B0와 B2 모두에 남았다. v0.2.0에 넣은 "새로 쓴 도입이 뒤를 되풀이하지 않는가" 점검은 효과를 확인하지 못했다.

## 6. 자동 선택

스킬을 프로젝트 스킬로 설치한 새 세션에 `/geulppal` 없이 요청을 줬다(v0.2.0, 요청 22개 × 2회, Edit·Write 허용). 요청은 스킬 설명을 읽은 사람이 썼다. 결과는 [`trigger-v0.2.0-r2.md`](2026-10-27-trigger/trigger-v0.2.0-r2.md)에 있다.

| | 실제 Claude의 선택 | 단어 겹침 대리 지표(모델 호출 없음) |
|---|---|---|
| 써야 하는 요청(12개) | 실행 21/24. 모든 회차 선택 10개, 한 번 이상 11개 | 20/24 |
| 쓰지 말아야 하는 요청(10개: 코드 구현·수정, 정보 조회, AI 작성 여부 판별 등) | 0/20 | 2/20 |

- 놓친 요청은 영어 두 개다: README의 마케팅 문구 다시 쓰기 0/2, 문서 단락 다듬기 1/2. 스킬 설명이 한국어 위주인 것이 원인일 수 있지만 확인하지 않았다.
- 대리 지표는 AI 작성 여부 판별 요청을 선택으로 예측했다. 실제 Claude는 선택하지 않았다.
- v0.1.0과 v0.2.0의 `description`은 같다. 다만 v0.1.0으로는 자동 선택 평가를 돌리지 않았다.
- 추가 확인(v0.2.1): README와 스킬 설명을 영어·한국어로 함께 쓰기로 하면서 `description`에 영어 작업 키워드를 더했다. 같은 요청 22개 × 2회로 다시 돌린 결과, 써야 하는 요청 23/24(모든 회차 선택 11개, 한 번 이상 12개), 쓰지 말아야 하는 요청 0/20이었다. 대리 지표는 20/24, 2/20으로 같았다. 이 요청들을 본 뒤 설명을 고쳤으므로 개발 확인이다. 스킬 본문은 v0.2.0과 같아 품질 평가 결과는 그대로 적용된다. [결과](2026-10-27-trigger/trigger-v0.2.1.md)

## 8. 판정자와 평가 기준의 한계

- **의미 판정의 흔들림**
  - 개발 사례에서 판정 지침을 고친 뒤 76건을 다시 판정했다. 바뀐 6건 중 2건(A `personal-blog-voice`)은 지침 변경과 관련 없이 판정만 달라졌다.
  - A `summary-request`에서는 같은 문제("의견"을 결론처럼 씀)를 1회차는 통과, 2회차는 실패로 판정했다.
  - 처음 보는 사례에서 두 판정의 일치는 68/72였다.
- **판정 지침 보완**
  - 메모로 밝힌 새 약속을 통과시킨 판정이 있어서, "본문에 들어간 새 사실·약속은 메모에서 밝혀도 실패"를 지침에 추가했다.
  - 이 보완은 B에 불리한 방향이다. 다시 판정한 결과 지침 변경과 관련된 건은 A 3건과 B0 1건이 통과에서 실패로 바뀌었다.
  - 이전 판정은 `2026-10-27-dev/records.json`의 `judge/meaning-rubric1/` 항목에 그대로 있다.
- **문자열 검사 오류**: 원문을 다시 싣지 않은 "고칠 곳 없음" 답변을 실패로 셌다. 세 조건이 각 2건씩 영향을 받았고, 고친 뒤 다시 계산했다([변경 이력](../CHANGELOG.md)).
- **순서에 따른 품질 판정 변화**: 처음 보는 사례의 품질 판정에서 순서를 바꾸면 결과가 바뀐 쌍이 18/40으로 많았다. 개발 사례에서는 4/27이었다.
- **판정자 구성**: 판정자는 작성 모델과 다른 모델이지만 같은 회사의 모델이다. 판정 모델 하나만 썼다.
- **평가 자료의 출처**: 처음 보는 사례도 실제 사용자 문서가 아니라 모델이 만든 가상 문서다. 판정 기준 일부는 실행 전에 고쳤다.
- **평가 범위**: 작성 모델 하나(`claude-sonnet-5-5`, effort high)와 붙여 넣은 글의 편집만 평가했다. 파일을 직접 고치는 흐름의 품질은 평가하지 않았다.

## 9. 다음 개선 후보 (적용하지 않음)

처음 보는 사례에서 관찰했다. 이것을 보고 고치면 이 사례들은 개발 자료가 되므로, 이번에는 적용하지 않았다.

- 진단 요청: `SKILL.md`의 "진단이나 전후 비교를 요청받았을 때만 문제 문장·이유·수정안을 보여준다"는 수정안을 내도 된다고 읽힐 수 있다. "고친 문장은 쓰지 마"라는 요청과 충돌한다.
- 조건의 범위: "해외에 계셔서" 같은 적용 조건을 예시("등")로 넓히지 않는 기준이 필요하다.
- 훑어 읽는 글: 상세페이지·공지처럼 훑어 읽는 글에서 재구성을 지나치게 삼가는지 확인이 필요하다.
- 영어 요청: 영어 요청에서 자동 선택이 약하다. `description`에 영어 사용 맥락을 보강할 수 있다.

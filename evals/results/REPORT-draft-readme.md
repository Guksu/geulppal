# 글빨 4차 평가 보고서: 원문 없이 README 쓰기 (2026-10-28)

1~3차 평가는 모두 원문이 있는 글을 고치는 사례였다. 하지만 글빨의 주 용도는 원문 없이 "README를 써 줘", "보고서를 써 줘"처럼 글을 새로 쓰는 일이다. 4차에서는 그 첫 장르로 README를 다뤘다. 작성 모델에게 저장소 코드만 주고(두 사례는 메모도) README를 처음부터 쓰게 했다.

판정은 모델(`claude-opus-5-5`)이 했고, README 초안 18쌍은 저장소 소유자가 블라인드로 비교했다. 0.4.0에서 나온 외부 링크 문제를 고친 0.4.1도 이 보고서에 함께 적는다(6절).

- **좋아진 것**

- **사람 블라인드 비교**: 저장소 소유자는 0.4.0 결과를 사람 README보다 8 대 0으로, 글빨 없음보다 3 대 0(비슷함 3)으로 골랐다. 0.3.0과는 1 대 1(비슷함 2)로 차이가 없었다. 판정 모델만 모델 글을 고르는 것은 아니었다. 다만 평가자가 한 명이고, 사람 README에는 배지·영어 문단처럼 사람 글임을 짐작할 단서가 있었다.

## 2. 판정

원문이 없으므로 "원문의 뜻을 지켰는가" 대신 "쓴 내용에 근거가 있는가"를 봤다([`draft-claims.md`](../judge/draft-claims.md)).

- 판정 모델이 작업 폴더의 같은 코드를 Read·Glob·Grep으로 읽고, 결과에서 설치 명령·함수 이름·옵션·수치·링크 같은 구체적인 주장을 뽑아 근거를 찾는다.
- 근거와 어긋나는 주장(contradicted)이나 근거를 찾지 못한 구체적 주장(unsupported)이 하나라도 있으면 실패다. 근거를 찾지 못했다는 것이 틀렸다는 뜻은 아니다. 예를 들어 `date-fns.org` 링크는 실제로 맞는 주소일 수 있지만, 사용자가 준 자료로는 확인할 수 없다.
- 사람 README(H)를 같은 기준으로 판정하면 8편 모두 실패했다(회차 1만 판정). 사람은 코드 밖에서 아는 내용(배포 상태, 벤치마크, 위키 링크)을 함께 쓰기 때문이다. 이 기준은 "주어진 자료로 확인할 수 있는 내용만 썼는가"를 보는 것이지 README의 좋고 나쁨을 보는 것이 아니다.

품질은 순서를 바꿔 두 번 묻는 짝 비교로 봤다. 고치는 일에 맞춘 기존 기준 대신 새로 쓴 글용 기준([`draft-quality.md`](../judge/draft-quality.md))을 썼다. 처음 보는 독자가 무엇인지·어떻게 시작하는지 찾을 수 있는가, 분량과 형식이 내용에 맞는가 등을 본다. 두 결과가 모두 근거 판정을 통과한 쌍만 비교했다.

품질 비교는 "해당 열의 조건이 앞선 수 대 상대가 앞선 수"다.

| 개발용 4개 × 2회 | 글빨 없음 | 0.3.0 | 1라운드 후보 | 2라운드 후보(0.4.0) |
|---|---|---|---|---|
| 근거 판정 통과 | 4/8 | 7/8 | 6/8 | 6/8 |
| 0.3.0과 품질 비교 | | | 3 대 1 (같음 2) | 3 대 0 (같음 1, 엇갈림 2) |
| 글빨 없음과 품질 비교 | | 0 대 2 (같음 1, 엇갈림 1) | 0 대 0 (같음 1, 엇갈림 2) | 2 대 1 (엇갈림 1) |

- 1라운드: `새 글 쓰기` 절을 넣었다. 자료를 먼저 읽고 함수 정의를 연다, 처음 읽는 독자의 질문(무엇인가, 왜 필요한가, 어떻게 시작하나, 무엇을 조심하나) 순서로 쓴다, 소개한 기능마다 쓰는 방법을 보인다, 자료 밖 사실(외부 링크·지원 환경·배포 여부)을 보태지 않는다, 메모 수치를 적힌 그대로 옮긴다, 예시 출력은 근거가 있을 때만 쓴다. [문서별 판단](../../skills/geulppal/references/document-types.md)에 README 초안 순서도 넣었다. 예시는 평가 사례와 다른 일반 예로 골랐다.
- 1라운드 결과에서 메모의 말투(`다시 잼`)를 표에 그대로 옮기고, 단위가 없는 수치를 그대로 둬 비교 대상이 모호해졌다. 같은 예시를 두 번 싣거나 디버깅 옵션까지 늘어놓는 경우도 있었다.
- 2라운드: 메모의 줄임말과 말투는 문장으로 풀되, 단위·비교 대상이 없으면 짐작하지 않고 완성문 밖에서 확인을 요청하게 했다. 같은 예시 반복과 독자가 쓰지 않을 디버깅·개발용 옵션을 뺄 내용에 넣었다. 2라운드 후보를 0.4.0으로 고정했다.

## 4. 확인

| | 글빨 없음 | 글빨 0.3.0 | 글빨 0.4.0 |
|---|---|---|---|
| 확인용 4개 × 2회 근거 판정 | 3/8 | 6/8 | 7/8 |

확인용의 글빨 없음·0.3.0 결과는 기준선 실행을 그대로 썼다. 새 확인용은 세 조건을 같은 날 같은 설정으로 실행했다.

0.4.0이 새 확인용에서 실패한 4회:

- `toss-date-readme` 2회: 코드에 없는 `date-fns.org` 링크 두 개
- `kobert-transformers-readme` 1회: DistilKoBERT에 `token_type_ids`를 넘기지 말라는 제약. 코드로 확인되지 않는다.
- `toss-use-funnel-readme` 1회: react-query의 Suspense 설정이 `withState`를 쓸 때만 필요한 것처럼 썼다. 코드로는 `useFunnel`만 써도 필요하다. 0.3.0도 같은 사례에서 같은 오류를 1회 냈다.

품질 비교(둘 다 근거 판정을 통과한 쌍):

| | 0.4.0 우세 | 상대 우세 | 같음 | 엇갈림 |
|---|---|---|---|---|
| 글빨 없음 대 0.4.0 (8쌍) | 5 | 0 | 0 | 3 |
| 0.3.0 대 0.4.0 (12쌍) | 5 | 1 | 1 | 5 |

판정 이유에서 0.4.0이 앞선 점은 다음과 같았다.

- 첫 부분에 바로 쓸 수 있는 사용 예를 둔다.
- 시작 전에 필요한 설정(Provider·Suspense)과 실제로 걸릴 수 있는 주의(`setState`가 값을 합치지 않는다)를 적는다.
- 사용법을 API 표로 다시 늘어놓거나 개발 명령 절을 붙이지 않아 작은 패키지에 맞는 분량이다.

0.3.0이 앞선 1쌍(`toss-use-query-param-readme`)에서는 0.4.0이 이 패키지가 왜 필요한지(첫 렌더링에서 쿼리 값이 비어 있는 문제)를 설명하지 않았다. `kobert-transformers-readme`에서는 0.4.0이 같은 토크나이즈 예제를 세 번 실었다는 지적이 있었다. 지침에 넣은 "같은 예시의 반복" 금지가 늘 지켜지지는 않았다.

### 고치는 글 회귀 확인

0.4.0의 새 절이 고치는 일에 영향을 주는지 3차의 사람이 쓴 README 16개 × 2회로 다시 확인했다. 의미 보존 31/32로 0.3.0과 같았고, 실패한 사례도 0.3.0과 같은 `khaiii-performance-deslop`이었다(`다소 느려졌습니다` → `느려졌습니다`).

## 5. 한계

- 판정 모델의 근거 판정이 일관되지 않은 경우가 있었다.
  - 기준선 khaiii 사례 4회는 모두 단위가 없는 메모 수치에 `초`를 붙였다. 판정 모델은 이를 통과시키고, 같은 사례에서 `바이트`를 붙인 1회만 실패로 봤다. 같은 기준을 적용하면 기준선의 글빨 없음은 6/16, 0.3.0은 11/16이다.
  - 감싸는 라이브러리의 사용 예(`ky.get(...).json()`)를 어떤 판정에서는 근거 있음으로, 어떤 판정에서는 근거 없음으로 봤다.
- 사례가 작고 분야가 치우쳐 있다(한국어 NLP 라이브러리와 toss/slash 패키지). 새 확인용 5개 중 4개가 같은 저장소의 작은 패키지라, 세 조건 모두 근거 판정을 쉽게 통과했다.
- 판정 모델은 사람 README보다 모델 결과를 거의 항상 골랐다. 품질 비교 결과는 사람 평가로 확인해야 한다.
- 실행 중 계정 사용량 제한에 걸려 일부 판정과 회귀 실행이 실패했고, 제한이 풀린 뒤 같은 설정으로 다시 실행했다. 실패한 시도도 기록에 남아 있다.
- 작성 모델 CLI는 2.1.312로, 3차(2.1.311)와 다르다.

## 6. 0.4.1: 외부 링크 고치기

0.4.0이 근거 판정에서 떨어진 링크는 모두 감싸는 라이브러리나 의존성의 공식 문서 주소였다(`date-fns.org`, `huggingface/transformers`). 독자가 모르는 바탕 개념을 풀어 주라는 지침이 외부 문서를 끌어온 것으로 보고 다음을 고쳤다.

- 링크는 자료에 적힌 주소(패키지 설정의 `repository`·`homepage`, 코드와 주석의 URL, 메모)만 쓴다. 의존성의 공식 문서도 자료에 주소가 없으면 이름만 적는다.
- 바탕 개념을 외부 문서 링크로 대신하지 않는다.
- 다른 라이브러리의 동작에서 나오는 사용 제약을 보태지 않고, 비슷한 함수가 같은 인자를 받는다고 미루어 쓰지 않는다.
- 완성 점검에 "링크마다 자료 어디에 그 주소가 있는지 댈 수 있는가"를 넣었다.

새 확인용 5개는 0.4.0을 분석하며 결과를 읽었으므로, 고치기 전에 2차 새 확인용 4개(Hangul.js, KoBERT, g2pK, toss/slash `sentry`)를 만들어 커밋했다. 한 번만 고치고 고정했다.

| | 글빨 없음 | 글빨 0.4.0 | 글빨 0.4.1 |
|---|---|---|---|
| 근거 판정: 개발용 4개 × 2회 | 4/8 | 6/8 | 5/8 |
| 근거 판정: 새 확인용 5개 × 2회(이번에 고친 근거) | 9/10 | 6/10 | 10/10 |
| 근거 판정: 2차 새 확인용 4개 × 2회 | 2/8 | 8/8 | 8/8 |
| 2차 새 확인용 실행당 비용(USD) | 0.173 | 0.296 | 0.289 |

- 근거 없는 링크: 0.4.0은 새 확인용에서 4개(2회), 0.4.1은 위 세 묶음 모두에서 0개였다.
- 0.4.1 개발용 실패 3회는 Korpora의 어려운 API(리스트 인자, 인자가 맞지 않아 생성되지 않는 클래스) 2회와 khaiii의 "C++로 만든 라이브러리" 1회다.
- 2차 새 확인용에서 글빨 없이 쓴 README는 8회 중 6회 떨어졌다. 0.4.0과 0.4.1은 모두 통과해, 링크 수정의 효과를 처음 보는 사례로는 확인하지 못했다.

품질 비교(둘 다 근거 판정을 통과한 쌍):

| | 0.4.1 우세 | 상대 우세 | 같음 | 엇갈림 |
|---|---|---|---|---|
| 0.4.0 대 0.4.1, 고친 근거로 쓴 9개 | 2 | 4 | 2 | 3 |
| 0.4.0 대 0.4.1, 2차 새 확인용 4개 | 0 | 3 | 2 | 3 |
| 글빨 없음 대 0.4.1, 2차 새 확인용 4개 | 2 | 0 | 0 | 0 |

0.4.0이 앞선 쌍의 판정 이유는 같은 예시를 다시 싣는다, 일반적인 BERT 설명이나 요구 버전 표를 옮겨 적었다, 주의 사항을 끝에 모았다, 감싸는 라이브러리의 호출 예가 없다는 것이었다. 마지막 이유는 외부 지식을 더 엄격하게 막은 영향일 수 있다.

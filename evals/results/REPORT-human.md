# 글빨 2차 평가 보고서: 사람이 쓴 글 (2026-10-27)

1차 평가의 사례는 모두 모델이 만든 가상 문서였다. 2차에서는 국내 글쓰기 자료를 조사하고, 2024년 이전에 사람이 쓴 공개 글로 평가 사례를 만들었다. 그 결과로 스킬을 두 라운드 고쳤고, 고정한 버전을 처음 보는 사람 글로 확인했다. 판정은 모두 모델(`claude-opus-5-5`)이 했다. 사람의 평가는 하지 않았다.

조사 내용은 [국내 글쓰기 자료와 사람이 쓴 글](../../research/korean-sources.md)에 있다. 사례 구성과 만드는 방법은 [사람이 쓴 글 평가](../human/README.md)에, 1차 평가는 [평가 보고서](REPORT.md)에 있다.

## 요약

확인용 사례는 스킬을 고정한 뒤 처음 돌린 사람 글 5편, 사례 9개다. 각 사례를 2회 실행했다.

| | 글빨 없음 | 글빨 0.2.1 | 글빨 0.3.0 |
|---|---|---|---|
| 확인용 사례 의미 보존(9개 × 2회) | 8/18 | 16/18 | 16/18 |
| 확인용 사례 품질 비교(0.3.0과) | 2 대 2 (엇갈림 3) | 3 대 2 (같음 5, 엇갈림 4) | |
| 실행당 시간 중앙값(확인용) | 15.3초 | 19.9초 | 22.4초 |
| 실행당 비용(확인용, USD) | 0.045 | 0.085 | 0.097 |

- **좋아진 것**
  - 글빨은 사람 글에서도 사실과 확실성을 더 잘 지켰다. 기준선 18개 사례 전체에서 의미 보존은 글빨 없음 15/36, 0.2.1 32/36이었다. 글빨 없음이 실패한 21회 가운데 15회는 확실성이 바뀐 경우였다. "접수가 가능하다고 합니다"처럼 전해 들은 말을 "접수합니다"로 단정하거나, 추측을 사실처럼 쓴 경우가 많았다. AI 티를 빼 달라는 요청에서는 필자가 겪지 않은 경험을 1인칭으로 지어낸 경우도 있었다.
  - 1차 평가에서 남아 있던 실패 세 가지가 0.3.0 후보에서 사라졌다. 하나는 조건을 넓히는 오류(`해외에 계셔서` → `해외 체류 등으로`)다. 0.2.0은 2회 모두 실패했고 0.3.0은 2회 모두 통과했다. 진단만 요청한 사례도 0.2.0은 2회 모두 실패했고 0.3.0은 2회 모두 통과했다. 사실로 새 글을 쓰는 사례(`draft-from-facts`)에서 기능을 지어내는 오류는 0.2.0이 2회 중 1회 냈고, 0.3.0은 내지 않았다. 다만 이 사례들의 실패를 보고 스킬을 고쳤으므로 독립적인 결과는 아니다.
- **나빠졌거나 나아지지 않은 것**
  - 확인용 사례에서는 0.3.0이 0.2.1보다 낫다는 근거를 얻지 못했다. 의미 보존은 16/18로 같았고, 품질 비교도 3 대 2로 차이가 없었다.
  - 0.3.0도 확인용 사례에서 추측을 단정으로 바꾼 실패가 있었다("가장 어려울 텐데" → "가장 어려운 일은 …이다"). 기대 표현의 시제를 바꾼 실패도 있었다("기대가 된다" → "기대됐다").
  - 1라운드 후보(0.3.0-r1)는 개발용 사례의 의미 보존이 18/18이었다. 하지만 품질 비교에서 0.2.1에 6쌍을 지고 1쌍도 이기지 못했다. 어색한 호응과 반복을 덜 고쳤고, 짧은 후기에서 소제목을 모두 지운 결과에는 판정이 엇갈렸다. 2라운드에서 이 부분을 되돌리고 보완했다.
  - 스킬 본문이 길어져 0.2.1보다 실행당 비용이 약 14%, 입력 토큰이 약 12% 늘었다(확인용 사례 기준).
- **채택한 수정**: 0.3.0(2라운드 후보)을 새 버전으로 둔다. 근거는 다음 세 가지다. 국내 자료와 사람 글에서 관찰한 기준(전해 들은 말·추측 보존, 범위어, 번역투 판단)을 담았다. 1차에서 알려진 실패를 고쳤다. 확인용 사례에서 0.2.1보다 나빠지지 않았다. 처음 보는 글에서 품질이나 정확성이 나아졌다는 근거는 없다.
- **확인하지 못한 것**
  - 사람 독자의 평가
  - 다른 작성 모델(`claude-sonnet-5-5` 하나만 썼다)
  - 영어 사람 글. 이번 사람 글 사례는 모두 한국어다
  - 자동 선택. 스킬 설명(`description`)은 바꾸지 않았고 자동 선택 평가는 다시 하지 않았다

## 1. 조사

국립국어원 『새국어생활』 2012년 봄호 특집 「번역과 국어」의 글 세 편과 안정효 인터뷰를 PDF 전문으로 읽었다. 같은 호에 실린 2011년 보도자료 언어 진단 소식도 읽었다. 이오덕, 김정선, 이희재의 책과 안정효의 『글쓰기 만보』는 본문을 읽지 못해 근거로 쓰지 않았다.

조사에서 스킬 후보로 정리한 기준은 네 가지다.

1. 번역투 표현은 틀린 문법이 아니므로 금지하지 않는다. 다만 같은 뜻을 더 자연스럽게 쓸 수 있으면 바꾼다. 대상은 `~을 가지고 있다`, `~에 있어서`, `~로부터`, `~을 통해`, `~에 의해`, `-의`가 이어진 명사구, 습관적인 `-들`이다.
2. 주제어 `는` 뒤와 문장 첫 접속사·부사 뒤의 쉼표가 읽는 데 필요한지 본다.
3. 뜻을 더하지 않는 `있다·것·수`의 겹침을 줄인다.
4. 전해 들은 말과 추측·의견 표시를 남긴다.

쉼표 비율이나 표현 개수 같은 수치 기준은 쓰지 않았다.

## 2. 사람이 쓴 글 사례

대한민국 정책브리핑의 정책기자단 기사 8편과 정책뉴스 2편(2018~2022년, 공공누리 제1유형)을 발췌했다. 원문 하나로 두 사례를 만들었다.

- **polish**: 원문을 그대로 주고 다듬어 달라고 한다(10개).
- **deslop**: 스킬 없는 별도 세션이 원문을 "더 전문적이고 매력적으로 풍성하게" 고친 글을 주고, AI 티를 빼 달라고 한다(8개).

deslop 입력은 판정 모델이 원문과 대조해 사실이 그대로인지 검수했다. 10편 중 6편은 첫 시도에서 통과했고, 2편은 다시 만든 뒤 통과했다. 나머지 2편은 세 번 모두 통과하지 못해 deslop 사례를 만들지 않았다. 실패 이유는 대부분 전해 들은 말을 단정으로 바꾸거나(`이용했다고 한다` → `함께했다`), 필자의 생각을 당위로 바꾸거나, 원문에 없는 감상을 넣은 것이었다. 스킬 없이 "더 매력적으로" 고쳐 달라고 하면 이런 변경이 흔히 생긴다는 점을 보여 준다.

원문 10편을 개발용 5편(사례 9개)과 확인용 5편(사례 9개)으로 나눴다. 스킬을 고칠 때는 개발용 결과만 봤다. 사례·요청·판정 기준은 기준선 실행 전에 커밋했다(`0e4921e`).

품질 비교에는 사람 원문을 기준 조건 H로 넣었다. polish에서 H는 고치지 않은 입력이고, deslop에서는 부풀리기 전의 원문이다.

## 3. 기준선: 글빨 없음(A)과 글빨 0.2.1(B)

18개 사례를 조건마다 2회 실행했다.

| | A | B | H(사람 원문) |
|---|---|---|---|
| 의미 보존 | 15/36 | 32/36 | 32/36 |
| 개발용 / 확인용 | 7/18 / 8/18 | 16/18 / 16/18 | 16/18 / 16/18 |

A의 실패 21회를 일반 검사별로 세면 다음과 같다. 한 실행이 여러 검사에 걸릴 수 있다.

- 확실성 변경 15회
- 새 사실 11회
- 누락 7회
- 조건 4회

B의 실패 4회는 다음과 같다.

- 범위어를 넣은 경우: `온라인으로 받았다` → `온라인으로만 받았다`
- 문장을 합치다 "24시간 신청 가능"을 뺀 경우
- 방문기에서 "기대가 크다"는 기대 표현을 지운 경우
- 안내문의 "지난해 긴급재난지원금과 달리"를 "지난해 긴급재난지원금처럼"으로 바꿔 비교를 뒤집은 경우

H의 실패 4회는 사람 원문의 문제가 아니라 평가 구조에서 나왔다. 2회는 polish 사례에서 고치지 않은 입력이 "안내문으로 고쳐 달라"는 요청을 따르지 않았다고 판정된 경우다. 나머지 2회는 부풀린 글이 원문의 "가장 짜릿함"을 "손꼽히는 짜릿함"으로 바꿨고, 검수에서 이를 놓쳐 원문 쪽이 오히려 더 강한 평가를 한 것으로 판정된 경우다.

품질 비교는 다음과 같다. 두 결과가 모두 의미 보존을 통과한 쌍만, 순서를 바꿔 두 번 판정했다.

| 비교 | 결과 |
|---|---|
| A 대 B | 5 대 4 (엇갈림 6) |
| H 대 A | 0 대 14 |
| H 대 B | 3 대 26 |

판정 모델은 거의 항상 사람 원문보다 고친 글을 골랐다. polish에서는 고치지 않은 원문이 한 번도 이기지 못했다. deslop에서는 사람 원문이 B에 3번 이기고 8번 졌다. 이것이 B의 글이 사람 글보다 낫다는 뜻인지, 판정 모델이 모델이 다듬은 글을 선호한다는 뜻인지는 이 평가로 구분할 수 없다. 사람 원문이 이긴 3번은 모두 후기·모집 글에서 B가 부풀린 글의 소제목 구성을 그대로 둔 경우였다.

## 4. 개선 라운드

개발용 9개 사례만 보고 고쳤다. 라운드마다 고친 후보를 다음 세 묶음에서 2회씩 실행했다.

- 사람 글 개발용 9개
- 1차의 처음 보는 사례 12개
- 1차의 개발 사례 19개

1차 사례 두 묶음은 회귀 확인용이다.

### 1라운드 후보(0.3.0-r1)

조사 결과와 개발용 실패를 반영했다.

- 구분할 것에 "전해 들은 말·직접 확인한 사실"을 넣고 `받을 수 있다고 합니다` → `받을 수 있습니다` 같은 변경을 막았다. 추측·의견 표시도 남기게 했다.
- `만`·`등`·`모두`·`항상`처럼 범위를 정하는 말을 새로 넣거나 빼지 않게 했다. 예시는 평가 사례와 다른 문장으로 새로 썼다.
- 번역투 판단표를 넣었다. 틀린 문법이 아니며 같은 뜻을 더 자연스럽게 쓸 수 있을 때만 바꾼다고 적었다.
- 점검 목록에 "합치거나 지운 문장에만 있던 사실도 남았는가"를 넣었다.
- 고친 글을 쓰지 말라는 진단 요청에는 대체 문구도 쓰지 않게 했다.
- 후기 글에 덧붙은 소제목을 문단으로 되돌리게 했다. 공공 안내문 기준도 문서별 판단에 넣었다.

| | B(0.2.1, 0.2.0) | 0.3.0-r1 |
|---|---|---|
| 사람 글 개발용 의미 보존 | 16/18 | 18/18 |
| 1차 처음 보는 사례 의미 보존 | 18/24 | 22/24 |
| 1차 개발 사례 의미 보존 | 36/38 | 37/38 |
| 사람 글 개발용 품질(B 대 r1) | | 6 대 0 (같음 5, 엇갈림 5) |
| 1차 처음 보는 사례 품질(0.2.0 대 r1) | | 3 대 3 (같음 6, 엇갈림 6) |

1차 사례의 B는 0.2.0이다. 0.2.1과 본문이 같고 스킬 설명만 다르다.

의미 보존은 나아졌지만 사람 글 품질 비교에서 B에 졌다. 판정 이유는 두 가지였다.

- 어색한 호응과 가까운 반복을 덜 고쳤다. 단어를 바꾸며 어감을 놓친 경우도 있었다(`공교롭게도` → `마침`).
- 후기 글의 소제목을 모두 지운 결과에는 판정이 엇갈렸다. 사람 원문과 비교할 때는 소제목이 없는 쪽이 이겼다. B와 비교할 때는 "요청하지 않은 구조 변경", "찾기 어려워졌다"는 이유로 소제목을 남긴 쪽이 이겼다.

### 2라운드 후보(0.3.0-r2 = 0.3.0)

- 소제목 규칙을 되돌렸다.
- 다듬기 요청에서는 주어와 서술어가 맞지 않는 문장, 가까이 붙은 같은 단어의 반복, 꼬인 수식부터 고치되 원래 말의 어감과 평가를 지키게 했다. 예시는 평가 사례에 없는 `하필` → `마침`으로 들었다.
- 이메일·안내문도 문서별 판단을 읽게 했다. 이전에는 읽을 문서 목록에 없었다.
- 번역투 판단표의 "모두 찾아 바꾸지 않는다"는 중복이어서 뺐다.

| | B | 0.3.0-r2 |
|---|---|---|
| 사람 글 개발용 의미 보존 | 16/18 | 16/18 |
| 1차 처음 보는 사례 의미 보존 | 18/24 | 21/24 |
| 1차 개발 사례 의미 보존 | 36/38 | 37/38 |
| 사람 글 개발용 품질(B 대 r2) | | 1 대 0 (같음 5, 엇갈림 8) |
| 사람 글 개발용 품질(H 대 r2) | | 2 대 11 (엇갈림 1) |
| 1차 처음 보는 사례 품질(0.2.0 대 r2) | | 4 대 3 (같음 6, 엇갈림 3) |

r2의 사람 글 개발용 실패 2회는 `온라인으로만`(범위어 규칙을 넣었는데도 다시 나왔다)과 "조금 불편하기는 해도"를 "특히 그렇지만"으로 바꾼 평가 강도 변경이었다. 1차 처음 보는 사례의 실패 3회는 다음과 같다.

- 그대로 두라는 요청에서 원문 일부만 다시 실어 표기가 빠진 경우
- 5줄 요약을 6줄로 쓴 경우
- PR 본문에서 "iOS는 무관해서 테스트하지 않았다"를 뺀 경우

두 라운드를 마쳐 r2를 0.3.0으로 고정했다(`evals/snapshots/v0.3.0-r2`, 해시는 `hashes.json`).

## 5. 확인용 사례

고정한 0.3.0을 확인용 9개 사례에 2회씩 실행했다. A·B·H는 기준선 실행을 다시 썼다. 입력·모델·설정이 같다.

| | A | B(0.2.1) | 0.3.0 |
|---|---|---|---|
| 의미 보존 | 8/18 | 16/18 | 16/18 |
| polish / deslop | 5/10 / 3/8 | 9/10 / 7/8 | 8/10 / 8/8 |

## 7. 한계

- 사례가 적다. 확인용은 원문 5편, 사례 9개, 각 2회다. 0.2.1과 0.3.0의 차이는 1~2회 수준이라 우연과 구분할 수 없다.
- 판정은 모델이 했다. 판정 모델은 사람 원문보다 모델이 고친 글을 거의 항상 골랐다. 판정 모델이 모델의 문체를 선호할 수 있으므로, 품질 비교는 같은 모델이 만든 두 결과를 비교할 때만 참고한다.
- 이번에는 같은 결과를 두 번 판정하는 일치도 확인을 하지 않았다. 1차에서는 72건 중 4건이 달랐다.
- polish 사례에서 H는 고치지 않은 원문이다. 고쳐 달라는 요청에 아무것도 바꾸지 않은 결과로 판정되므로, H의 의미 보존 수치는 사람 글의 정확성을 뜻하지 않는다.
- 부풀린 글 검수가 평가 강도 변화 하나("가장" → "손꼽히는")를 놓쳤다. 이 사례에서는 H가 의미 보존을 통과하지 못해 H와의 품질 비교에서 빠졌다.
- 1차의 처음 보는 사례는 이번에 회귀 확인에 썼다. 그 실패를 보고 스킬을 고쳤으므로 더는 독립된 자료가 아니다.
- 원문은 정책브리핑의 정책기자단 기사와 정책뉴스다. 개인 블로그, 기술 문서, README 같은 다른 사람 글은 넣지 않았다. 2023년 이전 글을 골랐지만 사람이 썼는지 확인할 방법은 없다.
- 작성 모델은 `claude-sonnet-5-5` 하나, CLI는 2.1.311이다.
- 판정 도중 계정 사용량 제한에 걸려 품질 판정 102건이 비었다. 판정 스크립트가 빈 판정을 다시 하도록 고친 뒤 같은 판정 지침으로 다시 했다. 사용량 제한 메시지는 공개 기록에 남기지 않았다.

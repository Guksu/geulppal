# `pr-technical-literals`

[← 개발 사례 목록](README.md) · 수정 · pr · 한국어

## 요청

> PR 본문 문장을 다듬어줘. 코드와 링크는 유지해줘.

## 원문

> 이번 개선은 매우 혁신적입니다. `retryCount`가 0일 때 재시도하지 않도록 수정했습니다. 검증 명령은 다음과 같습니다.
>
> ```sh
> npm test -- retry.test.ts
> ```
>
> 위 테스트 8개가 통과했습니다. 전체 테스트는 실행하지 않았습니다. \[설명](docs/retry.md#retry-count)

<details><summary>평가 기준 (작성 모델에는 보여 주지 않음)</summary>

**남아야 할 것**

- retryCount
- 0일 때 재시도하지 않음
- 코드 블록 전체
- 8개 통과
- 전체 테스트 미실행
- docs/retry.md#retry-count

**있으면 안 되는 변경**

- 전체 테스트 통과로 확대
- 명령 변경
- 링크 대상 변경
- 새 홍보성 서명 추가

**글자 그대로 남아야 할 문자열**: `retryCount`, `npm test -- retry.test.ts`, `(docs/retry.md#retry-count)`

</details>

## 1회차

### 글빨 없음 — ✗ 의미 보존 실패

> ```markdown
> `retryCount`가 0일 때 재시도하지 않도록 수정했습니다.
>
> 검증 명령은 다음과 같습니다.
>
> ```sh
> npm test -- retry.test.ts
> ```
>
> 위 테스트 8개가 모두 통과했습니다. 전체 테스트는 실행하지 않았습니다.
>
> 자세한 설명은 [문서](docs/retry.md#retry-count)를 참고해 주세요.
> ```
>
> - **"이번 개선은 매우 혁신적입니다" 삭제:** 변경 내용을 설명하지 않는 평가성 문장이라 뺐습니다. 강조가 필요하면 "`retryCount`가 0이어도 재시도하던 문제를 수정했습니다"처럼 이전 동작을 적는 편이 리뷰어에게 더 도움이 됩니다.
> - **"8개가 통과했습니다" → "8개가 모두 통과했습니다":** 실패가 없었다면 이 표현이 더 분명합니다. 실패가 있었다면 원문대로 두세요.
> - **링크 문구:** `[설명]`을 문장 안에 넣어 `[문서]`로 바꿨습니다. 링크 경로와 앵커는 그대로입니다.
> - **코드 블록과 명령어:** 변경하지 않았습니다.

**의미 보존 실패 이유(판정 모델)**

- 본문의 '위 테스트 8개가 모두 통과했습니다'에 '모두'가 붙어 실패가 없었다는 주장이 생겼다. 원문에 없는 내용이며, 메모에서 조건부라고 밝혔어도 본문에 들어갔다(8개 통과 distorted, new_facts·status_certainty problem).

> ---
>
> 원문에 수정 전 동작(`retryCount`가 0일 때 어떻게 됐는지)이 없습니다. 검토자가 문제 상황을 알아야 한다면 한 문장을 직접 추가해 주세요. "매우 혁신적입니다"는 근거가 될 내용이 없어 뺐습니다.

## 2회차

### 글빨 없음 — ✗ 의미 보존 실패

> **수정본**
>

>
> 검증 명령은 다음과 같습니다.
>
> ```sh
> npm test -- retry.test.ts
> ```
>
> 위 테스트 8개가 모두 통과했습니다. 전체 테스트 스위트는 실행하지 않았습니다.
>
> 자세한 내용은 \[설명](docs/retry.md#retry-count)을 참고해 주세요.
>
> **변경 사항**
> - "이번 개선은 매우 혁신적입니다"는 삭제했습니다. 근거 없는 과장 표현이라 리뷰어에게 도움이 되지 않고, 변경 내용은 바로 다음 문장에 담겨 있습니다.
> - "전체 테스트는 실행하지 않았습니다"는 "전체 테스트 스위트는 실행하지 않았습니다"로 바꿨습니다. 범위가 더 분명해집니다.
> - 링크는 문장 안으로 넣어 "참고해 주세요"로 연결했습니다. 링크 주소와 코드 블록은 그대로입니다.
>
> "8개가 통과했습니다"에 "모두"를 넣었는데, 실패나 건너뛴 테스트가 있었다면 빼 주세요.

**의미 보존 실패 이유(판정 모델)**

- 본문에 '모두'를 넣어 "위 테스트 8개가 모두 통과했습니다"로 바꿨다. 원문에 없는 '실패·건너뜀 없음'이라는 주장을 더한 것이다. 메모에서 그렇다고 밝혔지만 본문에는 그대로 남아 있다.

두 결과가 모두 의미 보존을 통과했을 때만 비교했습니다. 판정 모델에는 어느 쪽이 글빨인지 알려 주지 않았고, 순서를 바꿔 두 번 판정했습니다.

<details><summary>1회차 글빨 0.1.0 vs 글빨 0.2.0: 판정 이유</summary>

**1번째 판정** (결과 X = 글빨 0.1.0, 결과 Y = 글빨 0.2.0) → 글빨 0.1.0 우세

두 결과 모두 근거 없는 수식을 지우고 코드와 링크를 유지했으며, 구성도 거의 같습니다. 차이는 Y의 첫 문장에 있습니다. "이 `retryCount`가…"는 원문 문장을 지우다 남은 "이" 때문에 비문이 됐고, 이 문장이 PR 본문의 첫 문장입니다. Y의 "위 명령으로 실행한 테스트" 같은 작은 개선이 이 오류를 상쇄하지는 못합니다.

**2번째 판정** (결과 X = 글빨 0.2.0, 결과 Y = 글빨 0.1.0) → 글빨 0.1.0 우세

두 결과는 \"매우 혁신적입니다\"를 지우고 코드와 링크를 유지하는 등 거의 같게 편집했습니다. 차이를 가른 것은 X 본문의 첫 문장입니다. \"이 `retryCount`가…\"에 \"이번\"을 지우다 남은 \"이\"가 붙어 있어, PR 본문 맨 앞에 오타가 보입니다. Y 메모가 조금 장황하고 짐작한 예시를 넣은 것은 단점입니다. 하지만 메모는 본문 밖에 있으므로, 본문 품질을 기준으로 Y가 낫습니다.

<details><summary>2회차 글빨 0.1.0 vs 글빨 0.2.0: 판정 이유</summary>

**1번째 판정** (결과 X = 글빨 0.1.0, 결과 Y = 글빨 0.2.0) → 글빨 0.1.0 우세

과장 표현은 둘 다 똑같이 뺐다. 차이를 만든 것은 Y의 "자세한 설명은 [설명]에 있습니다"라는 어색한 반복이다. X는 코드 블록과 결과 문장이 매끄럽게 이어지고, 링크 텍스트만 봐도 어떤 문서인지 알 수 있다. X가 링크 텍스트를 바꾼 것은 손을 조금 더 댄 것이지만, 이를 밝히고 되돌릴 수 있게 했기 때문에 문제는 크지 않다.

**2번째 판정** (결과 X = 글빨 0.2.0, 결과 Y = 글빨 0.1.0) → 차이 없음

X는 링크 문구를 그대로 지켜 요청을 더 엄격히 따랐다. 하지만 "자세한 설명은 [설명]에 있습니다"처럼 같은 단어가 겹쳐 어색하다. Y는 문장 연결이 더 자연스럽다("이 명령으로 실행한 테스트 8개", 끝에 둔 "참고하세요"). 대신 링크 문구를 바꿔 "링크 유지" 요청에서 약간 벗어났다. 장단점이 엇갈려 어느 쪽도 분명히 낫지 않다.

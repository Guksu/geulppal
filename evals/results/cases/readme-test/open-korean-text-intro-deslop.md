## 원문

> # open-korean-text
>
> **스칼라로 만든 한국어 처리기**
>
> open-korean-text는 스칼라로 쓰인 한국어 처리기입니다. 현재 텍스트 정규화, 형태소 분석, 스테밍을 지원합니다. 짧은 트윗부터 긴 글까지 모두 처리할 수 있습니다.
>
> ## 함께 만들어 가요
>
> 개발에 참여하고 싶으신 분은 \[Google Forum](https://groups.google.com/forum/#!forum/open-korean-text)에 가입해 주세요. 사용법이 궁금한 초보자부터 코드에 직접 기여하고 싶은 분까지 모두 환영합니다.
>
> 👉 \[설치 및 수정하는 방법 상세 안내](docs/contribution-guide.md)
>
> ## 우리가 지향하는 것
>
> open-korean-text의 목표는 빅데이터 등에서 간단한 한국어 처리를 통해 색인어를 추출하는 것입니다. 완전한 수준의 형태소 분석을 지향하지는 않습니다. 대신 필요한 핵심을 가볍게 짚어 내는 데 집중합니다.
>
> ## 네 가지 핵심 기능
>
> open-korean-text는 normalization, tokenization, stemming, phrase extraction, 이렇게 네 가지 기능을 지원합니다. 아래 예시로 각 기능이 어떻게 동작하는지 확인해 보세요.
>
> ### 1. 정규화 (normalization)
>
> 흐트러진 표현을 읽기 좋은 형태로 바로잡습니다.
>
> `입니닼ㅋㅋ` → `입니다 ㅋㅋ`, `샤릉해` → `사랑해`
>
> * 한국어를 처리하는 예시입니닼ㅋㅋㅋㅋㅋ → 한국어를 처리하는 예시입니다 ㅋㅋ
>
> ### 2. 토큰화 (tokenization)
>
> 문장을 의미 있는 단위로 나누고, 각 단위에 품사를 붙입니다.
>
> * 한국어를 처리하는 예시입니다 ㅋㅋ → 한국어Noun, 를Josa, 처리Noun, 하는Verb, 예시Noun, 입니다Adjective(이다), ㅋㅋKoreanParticle
>
> ### 3. 어근화 (stemming)
>
> 활용된 표현을 기본형으로 되돌립니다.
>
> `입니다` → `이다`
>
> * 한국어를 처리하는 예시입니다 ㅋㅋ → 한국어Noun, 를Josa, 처리Noun, 하다Verb, 예시Noun, 이다Adjective, ㅋㅋKoreanParticle
>
> ### 4. 어구 추출 (phrase extraction)
>
> 문장에서 핵심이 되는 단어와 어구를 뽑아냅니다.
>
> * 한국어를 처리하는 예시입니다 ㅋㅋ → 한국어, 처리, 예시, 처리하는 예시

> 바꾼 내용입니다.
> - "함께 만들어 가요", "우리가 지향하는 것", "네 가지 핵심 기능" 같은 수사적인 제목을 단순한 제목으로 바꿨습니다.
> - "모두 환영합니다", "핵심을 가볍게 짚어 내는 데 집중합니다", "읽기 좋은 형태로 바로잡습니다" 같은 꾸밈 문장은 뺐습니다.
> - 👉 이모지를 뺐습니다.
> - 정규화 절에서 같은 예시가 두 번 나와서 하나로 합쳤습니다.
> - 원문 첫 문단은 기능을 세 개(정규화, 형태소 분석, 스테밍)만 적었는데, 아래에는 네 개가 나옵니다. 아래 내용에 맞춰 네 개로 고쳤습니다. "형태소 분석" 대신 "토큰화"를 썼습니다. 의도와 다르면 알려 주세요.

**의미 보존 실패 이유(판정 모델)**

- 원문 "짧은 트윗부터 긴 글까지 모두 처리할 수 있습니다"를 "트윗 같은 짧은 글을 주로 염두에 두고 만들었습니다"로 바꿨다. 긴 글을 처리할 수 있다는 범위가 사라졌고, 원문에 없는 설계 의도와 지원 범위가 본문에 들어갔다. 메모에서 밝혔더라도 본문에 있으므로 문제다.

> - 첫 문단은 지원 기능을 "정규화, 형태소 분석, 스테밍"으로 적었는데, 아래에는 토큰화와 어구 추출을 포함한 네 가지가 나옵니다. 원문 그대로 두었으니 실제 지원 범위에 맞게 확인해 주세요.
> - "짧은 트윗부터 긴 글까지"는 "모두"만 뺐습니다. 긴 글 처리를 실제로 확인했는지는 문서만으로 알 수 없습니다.
> - 링크 대상은 바꾸지 않았고, 링크 문구만 "기여 안내"로 고쳤습니다.

### 사람 원문 — ○ 의미 보존 통과

> 스칼라로 쓰여진 한국어 처리기입니다. 현재 텍스트 정규화와 형태소 분석, 스테밍을 지원하고 있습니다. 짧은 트윗은 물론이고 긴 글도 처리할 수 있습니다. 개발에 참여하시고 싶은 분은 \[Google Forum](https://groups.google.com/forum/#!forum/open-korean-text)에 가입해 주세요. 사용법을 알고자 하시는 초보부터 코드에 참여하고 싶으신 분들까지 모두 환영합니다.
>
> \[설치 및 수정하는 방법 상세 안내](docs/contribution-guide.md)
>
> open-korean-text의 목표는 빅데이터 등에서 간단한 한국어 처리를 통해 색인어를 추출하는 데에 있습니다. 완전한 수준의 형태소 분석을 지향하지는 않습니다.
>
> open-korean-text는 normalization, tokenization, stemming, phrase extraction 이렇게 네가지 기능을 지원합니다.
>
> **정규화 normalization (입니닼ㅋㅋ -> 입니다 ㅋㅋ, 샤릉해 -> 사랑해)**
>
> * 한국어를 처리하는 예시입니닼ㅋㅋㅋㅋㅋ -> 한국어를 처리하는 예시입니다 ㅋㅋ
>
> **토큰화 tokenization**
>
> * 한국어를 처리하는 예시입니다 ㅋㅋ -> 한국어Noun, 를Josa, 처리Noun, 하는Verb, 예시Noun, 입니다Adjective(이다), ㅋㅋKoreanParticle
>
> **어근화 stemming (입니다 -> 이다)**
>
> * 한국어를 처리하는 예시입니다 ㅋㅋ -> 한국어Noun, 를Josa, 처리Noun, 하다Verb, 예시Noun, 이다Adjective, ㅋㅋKoreanParticle
>
> **어구 추출 phrase extraction**
>
> * 한국어를 처리하는 예시입니다 ㅋㅋ -> 한국어, 처리, 예시, 처리하는 예시

## 품질 비교

두 결과가 모두 의미 보존을 통과했을 때만 비교했습니다. 판정 모델에는 어느 쪽이 글빨인지 알려 주지 않았고, 순서를 바꿔 두 번 판정했습니다.

| 회차 | 비교 | 결과 |
|---|---|---|
| 1 | 글빨 없음 vs 글빨 0.3.0 | 비교 안 함(의미 보존 실패) |
| 2 | 글빨 없음 vs 글빨 0.3.0 | 글빨 0.3.0 우세 |
| 1 | 글빨 0.2.1 vs 글빨 0.3.0 | 차이 없음 |
| 2 | 글빨 0.2.1 vs 글빨 0.3.0 | 차이 없음 |
| 1 | 사람 원문 vs 글빨 0.3.0 | 글빨 0.3.0 우세 |
| 2 | 사람 원문 vs 글빨 0.3.0 | 글빨 0.3.0 우세 |
| 1 | 글빨 0.3.0 vs 0.3.1 후보 | 비교 안 함(의미 보존 실패) |
| 2 | 글빨 0.3.0 vs 0.3.1 후보 | 순서를 바꾸면 판정이 바뀜 |

<details><summary>2회차 글빨 없음 vs 글빨 0.3.0: 판정 이유</summary>

**1번째 판정** (결과 X = 글빨 없음, 결과 Y = 글빨 0.3.0) → 글빨 0.3.0 우세

과장을 덜어낸 범위는 X가 조금 더 넓고, 예시 형식도 X가 깔끔합니다. 하지만 X는 첫 문단의 기능 목록을 세 가지에서 네 가지로 고치고 "현재"를 지웠는데, 수정 내역에서 이를 밝히지 않았습니다. "흐트러진 표현", "의미 있는 단위"처럼 과장이 아닌 표현까지 건조하게 바꾼 것도 아쉽습니다. 요청은 담백하게 다듬어 달라는 것이었습니다. Y는 과장된 부분만 덜어내고 원문의 사실과 말투를 지켰습니다. 기능 개수가 서로 맞지 않는 점과 "모두"에 근거가 없다는 점도 사용자에게 확인을 요청했습니다. 그래서 Y가 더 적절합니다.

**2번째 판정** (결과 X = 글빨 0.3.0, 결과 Y = 글빨 없음) → 글빨 0.3.0 우세

두 결과 모두 구호성 제목, 이모지, 수식 문장을 잘 빼서 과장을 줄인 수준은 비슷합니다. 차이는 절제와 의미 보존에서 납니다. Y는 첫 문단의 지원 기능 목록을 아래 기능 목록에 맞춰 바꾸고 "현재"를 지웠지만, 변경 내용 설명에는 이를 적지 않았습니다. "모두 환영합니다"도 "이곳에서 받습니다"로 바꾸면서 원문의 환영하는 말투가 사라졌습니다. X는 원문의 사실 진술과 말투를 유지했고, 불일치와 근거가 부족한 주장은 따로 적어 작성자가 판단하도록 했습니다. 담백하게 고쳐 달라는 요청에는 X가 더 맞습니다.

</details>

<details><summary>1회차 글빨 0.2.1 vs 글빨 0.3.0: 판정 이유</summary>

**1번째 판정** (결과 X = 글빨 0.2.1, 결과 Y = 글빨 0.3.0) → 차이 없음

두 결과는 과장 표현을 거의 같은 방식으로 지웠고, 확인이 필요한 사항 두 가지도 똑같이 덧붙였습니다. X는 원문의 존칭을 살렸고, Y는 "초보자"와 "직접" 같은 원문 표현과 연결 문장을 더 많이 남겼습니다. 어느 쪽에도 결정적인 우위가 없어 비긴 것으로 판정합니다.

**2번째 판정** (결과 X = 글빨 0.3.0, 결과 Y = 글빨 0.2.1) → 차이 없음

두 결과는 같은 과장 표현을 같은 방식으로 제거했고, 본문 구조와 기능 설명도 거의 같다. 확인 메모도 같은 두 문제(기능 수 불일치, 긴 글 처리 주장의 근거 부족)를 짚었다. Y는 원문 표현을 조금 더 보존하고 메모가 더 구체적이다. X는 '예시는 아래와 같습니다'로 독자를 안내하고 '초보자'를 남겼다. 장점이 엇갈리고 차이가 사소해 어느 쪽도 분명히 낫지 않다.

</details>

<details><summary>2회차 글빨 0.2.1 vs 글빨 0.3.0: 판정 이유</summary>

**1번째 판정** (결과 X = 글빨 0.2.1, 결과 Y = 글빨 0.3.0) → 차이 없음

두 결과는 태그라인 삭제, 제목 정리, 근거 없는 문장 삭제, 확인할 점 메모까지 대부분 똑같이 고쳤습니다. X는 "모두"를 직접 빼서 과장 제거 요청에 조금 더 적극적으로 응했습니다. Y는 참여 안내 문장의 말투를 보존해 원문 존중 면에서 약간 낫습니다. 차이가 작고 기준별로 엇갈려 어느 쪽도 분명히 우세하지 않습니다.

**2번째 판정** (결과 X = 글빨 0.3.0, 결과 Y = 글빨 0.2.1) → 차이 없음

두 결과 모두 슬로건, 감탄조 제목, \"가볍게 짚어 내는 데 집중\", 예시 안내 문장 같은 과장 요소를 비슷하게 걷어냈습니다. 확인 메모도 같은 두 가지를 짚었습니다. Y는 \"모두\"를 직접 빼서 담백하게 고쳐 달라는 요청을 조금 더 적극적으로 반영했습니다. X는 존대 표현의 일관성과 원문 말투를 조금 더 잘 지켰습니다. 기준별로 엇갈리고 차이가 사소해서 어느 쪽도 분명히 낫다고 보기 어렵습니다.

</details>

<details><summary>1회차 사람 원문 vs 글빨 0.3.0: 판정 이유</summary>

**1번째 판정** (결과 X = 사람 원문, 결과 Y = 글빨 0.3.0) → 글빨 0.3.0 우세

Y가 더 낫습니다. Y는 과장된 표현("핵심", "우리가 지향하는 것", "함께 만들어 가요", "가볍게 짚어 내는 데 집중")만 골라 담백하게 고쳤고, 문서 구조와 기능 설명은 남겼습니다. 기능 수가 서로 맞지 않는 점도 사용자에게 알려 주었습니다. X는 과장을 줄이기는 했지만 제목, 섹션, 기능 설명까지 지워 찾기 어려워졌습니다. 또 "쓰여진", "네가지"처럼 어색한 표현이 다시 들어가서 요청 범위를 넘어 지나치게 바꿨습니다.

**2번째 판정** (결과 X = 글빨 0.3.0, 결과 Y = 사람 원문) → 글빨 0.3.0 우세

X가 낫습니다. 과장된 제목과 수식어(\"함께 만들어 가요\", \"핵심\", \"가볍게 짚어 내는 데 집중\", 👉)만 덜어 내고, README 구조와 기능 설명은 그대로 두었습니다. 요청대로 담백하게 고친 결과입니다. Y는 과장 표현은 줄였지만 문서 제목과 섹션 제목, 기능 설명 문장까지 지웠습니다. 그래서 독자가 내용을 찾기 어렵고, 주어 없이 시작하는 첫 문장과 \"쓰여진\", \"네가지\" 같은 어색한 표기도 새로 생겼습니다.

</details>

<details><summary>2회차 사람 원문 vs 글빨 0.3.0: 판정 이유</summary>

**1번째 판정** (결과 X = 사람 원문, 결과 Y = 글빨 0.3.0) → 글빨 0.3.0 우세

Y는 원문의 구조와 실제 기능 설명은 살리고, 홍보성 제목, 부제, 맺음말식 문장, 이모지처럼 과장된 부분만 골라 걷어냈다. 그래서 담백하게 고쳐 달라는 요청에 정확히 맞는다. X도 과장 문구를 지우긴 했지만 제목, 섹션, 기능 설명 문장까지 함께 없애 문서가 찾기 어렵게 됐다. 문단 연결도 끊겼고 \"쓰여진\", \"네가지\" 같은 어색한 표현도 새로 생겼다. Y가 문서 끝에 검토 메모를 붙인 점은 아쉽지만, 원문의 3기능/4기능 불일치를 짚어 주는 등 내용은 쓸모 있다.

**2번째 판정** (결과 X = 글빨 0.3.0, 결과 Y = 사람 원문) → 글빨 0.3.0 우세

X가 낫습니다. 두 결과 모두 과장된 표현은 비슷하게 줄였습니다. X는 문서 구조와 말투를 지키면서 과장된 부분만 정확히 걷어 냈습니다. Y는 요청하지 않았는데 제목과 섹션 구조를 없애고 문단을 합쳤습니다. 그 결과 찾기 쉬움과 흐름이 나빠졌고 어색한 표현도 새로 생겼습니다. X 끝에 붙은 메모는 요청에 없던 것이지만, 세 가지와 네 가지로 어긋나는 기능 수, 근거 없는 "모두" 주장을 지적하고 있어 작성자에게 도움이 됩니다.

<details><summary>2회차 글빨 0.3.0 vs 0.3.1 후보: 판정 이유</summary>

**1번째 판정** (결과 X = 글빨 0.3.0, 결과 Y = 0.3.1 후보) → 차이 없음

두 결과는 과장 제거와 구조 정리를 거의 똑같이 했다. Y는 "모두"를 실제로 빼서 요청에 조금 더 충실하지만, 어구 추출 설명 같은 불필요한 수정이 있고 확인 메모의 정확도가 떨어진다. X는 "모두"를 남겼지만 메모가 더 정확하고 간결하다. 장단점이 엇갈리고 차이가 작아 어느 쪽도 분명히 낫지 않다.

**2번째 판정** (결과 X = 0.3.1 후보, 결과 Y = 글빨 0.3.0) → 0.3.1 후보 우세

두 결과는 태그라인, '대신 필요한 핵심을 가볍게 짚어 내는 데 집중합니다', 예시 유도 문장 같은 과장 표현을 똑같이 지웠고 제목 구성도 같습니다. 차이는 '짧은 트윗부터 긴 글까지 모두'의 '모두'에 있습니다. 이 표현은 요청이 겨냥한 과장에 해당합니다. X는 이를 직접 빼고 메모로 알렸고, Y는 그대로 둔 채 사용자에게 판단을 넘겼습니다. Y가 원문 문장을 덜 고쳐 절제 면에서는 조금 낫지만, 요청 충족이라는 핵심에서 X가 앞섭니다. 다만 그 차이는 크지 않습니다.

</details>

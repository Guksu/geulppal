# 평가 사례 변경 이력

평가 사례의 요청(`request`)과 입력(`input`)은 결과를 본 뒤 바꾸지 않는다. 판정 기준을 고칠 때는 날짜, 바꾼 내용, 이유를 여기에 남긴다.

## 2026-10-27 — 첫 실행 전 점검

실행 결과를 보기 전에 기존 12개 사례를 점검했다. 요청과 입력은 바꾸지 않았다.

| 사례 | 바꾼 내용 | 이유 |
|---|---|---|
| 전체 | `task`·`genre`·`language`·`exact`·`origin`·`overlaps_skill_examples` 필드 추가 | 사례 종류별로 집계하고, 문자열 그대로 남아야 하는 부분을 판정 모델과 따로 검사하기 위해 |
| `missing-evidence` | `must_preserve`에서 "성능 측정 근거 없음"을 빼고, `must_not`에 "성능 개선을 측정으로 확인된 사실처럼 단정"을 추가 | 요청은 "짧게 쓸 수 있는 범위까지만 써줘"다. 측정 근거가 없다는 문장을 결과에 꼭 넣으라는 요구는 요청에 없다. 성능 언급을 아예 빼는 소개글도 요청을 지킨 결과인데, 이전 기준으로는 실패가 된다. 지켜야 할 것은 "근거 없는 성능 주장을 하지 않는 것"이므로 금지 항목으로 옮겼다 |
| `review-only` | `must_not`의 "완성문을 임의로 작성"을 "완성문이나 고쳐 쓴 문장을 제시"로 바꿈 | 요청은 "수정문은 아직 쓰지 마"다. 이전 기준은 전체 완성문만 걸러서, 문제 문장마다 수정안을 붙인 결과를 판정자가 다르게 해석할 여지가 있었다 |
| `benchmark-scope` | `must_not`에 "A가 모든 지표에서 앞섰다는 식으로 주장 범위 넓히기" 추가, `exact`에 `axe` | 원문 첫 문장("A가 압도적으로 뛰어났습니다")은 A가 더 느렸다는 자료와 함께 있다. 이 주장을 남기거나 덜어내는 것은 허용하되, 범위를 넓히는 편집은 실패로 본다. 원문 주장 자체를 지우라고 요구하지는 않는다 |
| `pr-technical-literals`, `english-terms-and-list`, `quotation-and-opinion`, `source-as-data`, `draft-from-facts`, `missing-evidence` | `exact`에 코드·명령·링크 대상·파일명·인용문 안쪽·고유 이름을 지정 | 문자열 검사는 정확히 같아야 하는 부분에만 쓴다. 모두 원문에 있는 문자열이다 |

기존 사례 중 9개는 스킬의 [문장 예시](../skills/geulppal/references/editing-examples.md)와 같은 상황을 다룬다(`overlaps_skill_examples: true`). 그래서 이 목록 전체를 개발·회귀 평가로만 쓰고 독립적인 성능 근거로 소개하지 않는다.

| `english-readme-slop` | 영어 README의 홍보성 도입·결론, 명령과 한계 보존 |

## 2026-10-27 — 처음 보는 자료(holdout) 실행 전 점검

최종 후보(v0.2.0-r2)를 고정한 뒤 별도 세션이 사례 12개를 만들었다(`holdout/generation.json`). 생성 원본은 `holdout/cases.generated.json`에 그대로 두었다. 실행 전에 판정 기준만 점검했고, 요청과 입력은 바꾸지 않았다.

원문에 있는 주장이나 구성을 그대로 남긴 결과를 의미 보존 실패로 만드는 기준이 있었다. 이런 기준은 의미 보존 원칙과 충돌한다. 남길지 덜어낼지는 품질 판정에서 다룰 문제이므로 해당 항목만 고쳤다.

| 사례 | 바꾼 내용 | 이유 |
|---|---|---|
| `pr-image-cache-ko-en` | `must_not` "OOM 문제가 해결되었다고 단정하기" → "본문의 '해결될 것으로 기대'를 '해결했다'로 강화하거나, 원문에 없는 해결 근거를 덧붙이기" | 원문 결론에 이미 "해결되었다고 할 수 있습니다"가 있다. 원문 문장을 그대로 둔 결과까지 실패로 만들지 않게 했다 |
| `product-pet-feeder-ko` | 홍보 주장을 "사실처럼 남기기" 금지 → "더 강하게 만들거나 근거처럼 바꾸기" 금지 | 원문 주장을 남긴 결과를 실패로 만들던 기준 |

## 2026-10-27 — 문자열 검사 적용 범위 수정(처음 보는 자료 의미 판정 후)

`noop-publisher-submission-guide-ko`에서 A·B0·B2 6회가 모두 원문을 다시 싣지 않고 "고칠 곳이 없다"고만 답했다. 문자열 검사(`exact`)는 결과에 원문이 실린다고 가정해서, 판정 모델이 통과로 본 6회를 모두 실패로 셌다. 손상될 문자열이 없는 결과이므로 평가 기준의 오류다.

`scripts/eval/judge.mjs`를 고쳤다. `task`가 `noop-check`이고 결과에 `exact` 문자열이 하나도 없으면 원문을 다시 싣지 않은 것으로 보고 문자열 검사를 적용하지 않는다. 일부만 빠진 경우는 그대로 실패다. 판정 모델은 다시 부르지 않았고 기존 판정으로 다시 계산했다(`judge.mjs rescore`). 수정 전 기록은 `results/2026-10-27-holdout/records.json`의 `judge/meaning-before-rescore/` 항목에 있다. 개발 평가의 `noop-check` 사례는 `exact`가 비어 있어 영향이 없다.

## 2026-10-27 — 공개 기록을 records.json으로 묶음

실행·판정 기록이 기록 하나당 파일 하나(989개)여서 검토하기 어려웠다. 실행 폴더마다 `records.json` 하나로 묶었다. 키는 원래 파일 경로이고 내용은 바꾸지 않았다. 묶기 전후로 집계(`report.md`, `summary.json`)와 사례별 페이지를 다시 만들어 비교했고 모두 같았다.

판정 지침은 실행 뒤에 고치지 않았다. 근거 판정이 같은 종류의 주장을 다르게 본 경우(단위 `초`와 `바이트`)는 [4차 보고서](results/REPORT-draft-readme.md)의 한계에 적었다.

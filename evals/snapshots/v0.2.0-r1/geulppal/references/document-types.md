# 문서별 판단

문서 유형에 맞는 부분만 읽는다. 아래 항목은 독자가 필요한 정보를 찾도록 돕는 기준이며 고정 목차가 아니다.

## README와 기술 안내

처음 보는 독자는 무엇을 하는 프로젝트인지, 언제 쓰는지, 어떻게 시작하는지 알아야 한다. 프로젝트의 대단함을 평가하는 문장보다 제공하는 동작과 실제 사용 예시를 앞에 둔다. 만든 이유를 요청받았다면 확인된 불편함과 동기를 도입에 둔다.

설치·실행 명령, 요구 버전, 라이선스, 기능별 적용 조건은 간결함 때문에 삭제하지 않는다. 설치만으로 매번 자동 적용되는 것처럼 약속하려면 그 동작이 확인되어 있어야 한다. 스킬 설치와 플러그인 설치에 따른 기능 차이도 유지한다.

비교 이미지가 있으면 무엇을 비교했는지, 어떤 실행을 선택했는지 설명한다. 측정치는 도구·지표·표본·버전·실행 횟수와 연결해 쓴다. 자동 접근성 검사 결과로 전반적인 디자인 품질이나 접근성 보장을 주장하지 않는다. 생성 시간과 빌드 시간처럼 서로 다른 지표의 이름도 섞지 않는다.

README가 길다면 반복되는 상세 설명을 기존 상세 문서로 연결할 수 있다. 다만 결론을 해석하는 데 필수적인 조건과 한계는 관련 결과 가까이에 남긴다. 새 문서 분리는 요청 범위와 유지보수 필요가 있을 때 선택한다.

표·배지·코드 블록은 용도를 보고 남긴다. AI 문체를 줄인다는 이유로 README의 모든 형식을 없애지 않는다.

## PR 본문과 릴리스 설명

검토자가 대화를 읽지 않아도 어떤 문제가 언제 발생했고 수정 후 어떻게 동작하는지 알 수 있게 쓴다. 영향이 작은 변경이면 몇 문장으로 충분하다. 템플릿이 있으면 따른다.

테스트는 실행한 범위와 결과를 적는다. 검증하지 않은 상태를 통과했다고 쓰지 않는다. 관련 없는 검증 내역을 늘어놓지 않는다. 과거 시도나 대화 순서보다 최종 변경과 남은 제약을 설명한다.

자동 작성 안내·서명은 사용자가 요청한 형식과 저장소 정책을 따른다. 새로운 홍보성 꼬리말을 붙이지 않는다. 필수 출처·라이선스·기여자 표기는 문체 정리를 이유로 제거하지 않는다.

## 기획서·제안서·업무 문서

결정, 제안, 가정을 문장 안에서 구분한다. `추가할 예정입니다`, `추가를 검토합니다`, `추가했습니다`를 같은 뜻으로 다루지 않는다. 일정·비용·담당자·완료 조건이 제공되었다면 유지하고, 빈칸을 그럴듯한 값으로 채우지 않는다.

비교표는 선택에 필요한 차이를 보여줄 때 쓴다. 모든 선택지를 균형 있게 보이게 하려고 근거 없는 장단점을 채우지 않는다. 결론이 아직 없으면 결정된 것처럼 끝내지 않는다.

정책의 `~해야 한다`, `~할 수 있다`, `~하지 않는다`는 강도가 다른 문장이다. 격식 있는 문서를 편하게 읽히게 만들더라도 의무·허용·금지의 범위는 바꾸지 않는다.

## 블로그·소개글·에세이

독자가 이 글을 읽을 이유를 실제 문제나 관찰에서 시작한다. 저자가 제공한 경험과 만든 이유는 보존한다. 업계 전체의 흐름이나 거창한 시대 진단을 새로 덧붙이지 않는다.

의견은 작성자의 의견으로 남긴다. 비유, 유머, 여운, 의도적인 반복은 맥락에서 작동하면 유지한다. 전문 문서와 같은 중립적인 문체를 모든 글에 적용하지 않는다. 사람이 쓴 느낌을 만들려고 실패담·취향·감정을 새로 지어내지 않는다.

독자에게 부탁할 행동은 필요한 만큼만 쓴다. 업데이트 계획이나 피드백 요청을 사용자가 넣어 달라고 했다면 남긴다. 이를 상투적인 마무리라는 이유로 삭제하지 않는다.

## 이메일과 짧은 안내

받는 사람이 알아야 할 내용, 요청 행동, 기한을 쉽게 찾도록 쓴다. 관계에 필요한 인사와 감사는 유지한다. 친근함을 위해 반말로 바꾸거나, 사무적인 공손함을 전부 군더더기로 처리하지 않는다.

이미 간단하고 정확한 문구는 그대로 둘 수 있다. 짧은 안내를 더 풍성하게 보이게 하려고 배경·비유·결론을 추가하지 않는다.
